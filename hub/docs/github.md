# GitHub connection

An administrator installs the GitHub App in GitHub, connects their own GitHub account in Remy, then chooses that installation and its repositories under Connections. The user token must belong to the same app as `GITHUB_APP_ID`. Selected repositories reuse workspaces by canonical origin; deselection preserves the workspace and its work but stops watching and hosted Git access.

Configure the existing `GITHUB_APP_ID` and private-key secret, plus the GitHub connection OAuth credentials and webhook secret described in `connections.md`. Grant repository metadata read, contents read/write, pull requests read/write, issues read/write and checks read. Subscribe to installation, installation_repositories, issue_comment, pull_request, pull_request_review, pull_request_review_comment, check_run and check_suite updates. Deliver to `/api/connections/github/webhook`.

Each member authorizes their own GitHub account. PR creation, reviews and comments use that member's token in the hub. Tokens never reach a computer or the browser. Personal computers retain their own `gh` login; hosted Git continues through the scoped installation proxy and now also requires current repository selection.

## Pull requests in the web app

Every read and write below uses the member's own GitHub connection in the hub, and every one checks membership and that the repository is the origin of a workspace the member can open. A computer session is refused on writes: it holds a member identity but never changes a pull request for them.

- `GET github/pull-requests` lists open pull requests on workspace origins, cached for a minute per member.
- `GET github/pull-request?repository=&number=` is what the list leaves out because GitHub computes it per pull request: `mergeable` and `mergeStateStatus`, the head commit, when it was opened, each check's start and finish time, link and first line, reviewer names, and which stack members conflict.
- `GET github/pull-request-reviewers?repository=&number=&q=` lists GitHub's suggested reviewers, then people who can be assigned in the repository, never the author.
- `GET github/pull-request-files` and `github/pull-request-images` read the diff and the signed attachment copies.
- `GET github/pull-request-review?repository=&number=` is what the Files tab reads beside the diff: GitHub's `viewerViewedState` for each file (`VIEWED`, `UNVIEWED`, or `DISMISSED` when a file changed after you read it), every review conversation with its path, line and original line, side, resolved and outdated state and comments, which of those comments are still `pending` in your review, and the author's login, since GitHub refuses an author's approval. Files and conversations page through GraphQL one connection at a time.
- `POST github/actions` with `workspaceId`, `number` and `action`: `merge` squash merges with `title`, `body` as the message and the `sha` the reader saw; `request-reviewers` with `reviewers` (logins); `ready` and `draft` change draft state; `comment` and `review` post. The Files tab adds `view-file` (`path`, `viewed`) through `markFileAsViewed` and `unmarkFileAsViewed`; `line-comment` posts one inline comment now at the head commit with `path`, `line`, `side` and an optional `startLine` on the same side; `pending-comment` adds a thread to your pending review, starting one at the head when there is none; `reply` with `threadId` posts a reply now, or with `pending: true` adds it to the pending review; `edit-comment` and `delete-comment` change only your own pending comments; `submit-review` with `event` (`COMMENT`, `APPROVE`, `REQUEST_CHANGES`) and an optional `body` submits the pending review, or creates a review when nothing is queued (a bare Comment needs a note). A conversation or comment named by id is read back first and refused unless it belongs to this pull request. The repository is the workspace's selected GitHub App repository, or else its origin. A write drops the member's cached list.

- `GET github/pull-request-activity?repository=&number=` is the Activity tab: GitHub's `timelineItems` (issue comments, submitted reviews with their line-comment count, and each head commit's check result once every check on it finished), what the hub sent to the thread watching the pull request, and `seenAt`, when you last opened Activity. The first read of a pull request records now as seen, so its history is not counted as new. `PUT github/pull-request-seen` with `repository` and `number` moves that mark. The tab's badge counts reviews, comments and check results newer than it, leaving out your own.
- `GET github/pull-request-ticket?repository=&number=` is the linked Linear issue, found with your own Linear account (`linear.md`): an issue the pull request is attached to (`attachmentsForURL`), else the issue its branch was made for (`issueVcsBranchSearch`), else an identifier such as `REMY-214` in the branch or title. It answers `{ ticket: null }` when Linear is not connected here or nothing matches, and is cached for five minutes per member and pull request.

What a thread posts through the hub with `github_action` (a comment, a review, a line comment or reply) ends with `<!-- remy-thread:<computer>:<thread>:<signature> -->`, an HMAC of the account, computer and thread under the hub's secret. Activity lifts it off the body and shows the comment's real author with "From a thread on <computer>"; a marker that does not verify names no thread. A person's own comments carry no marker.

## Watching a pull request

A pull request can be watched by one thread, the linked thread shown in its Summary under Watched by. `GET github/pull-request-follow?repository=&number=` says which thread watches it and whether GitHub's webhooks for that repository reach Remy (`receives`), which they do only through the GitHub App installed on it and selected under Connections. `PUT github/pull-request-follow` with `repository`, `number`, `computerId` and `threadId` starts watching; the hub reads that thread through its coordinator as you and refuses it unless it belongs to this account and you can write in it. `DELETE` stops it; the member who started it always can, anyone else needs write access unless the thread is gone. A computer session is refused on both.

Signed receipts are durable and deduplicated before processing (`connections.md`). For a watched pull request, `GitHubConnection.receive()` turns a new issue comment, a submitted review with a verdict or a note, a new line comment, and a check suite that failed or timed out into a message, with GitHub's words quoted as information rather than instructions, and records it on the receipt's `github_activity` row. Edits, bot comments, a review whose only content is line comments (each arrives on its own) and anything carrying a thread marker are not sent, so a thread never receives its own words back. The message goes to the thread as the member who started watching, through the same coordinator checks their own message would pass, with a message id derived from the receipt; `delivered_at` is set once the thread accepts it. An offline computer leaves it for the scheduled sweep, which retries every five minutes for a day. A thread that is gone or no longer writable by that member, a member who lost the workspace, or a closed pull request ends the watching; removing the installation ends all of it for the account. Nothing a webhook carries starts a thread.

The isolated QA provider replaces only vendor endpoints. The production OAuth broker, signature verification, queue, organization access, computer choice, computer connection and thread execution remain active. A live private-repository acceptance run still requires an installed app and a disposable repository authorized by its owner.
